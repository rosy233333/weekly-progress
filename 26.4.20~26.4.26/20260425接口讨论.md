## 现有设计

### 内核态加载与初始化

内核调用`load_and_init`实现vdso的加载和初始化。

#### load_and_init

```plain
/// 在加载vDSO的地址空间（通常是内核）中调用，同时加载vDSO和初始化VTABLE。
/// 
/// 若在一个地址空间中加载再映射到另一个地址空间中，需使用`map_and_init`。
/// 
/// 该函数的返回值为vDSO和vVAR的映射区域的信息，元组的三项依次为首地址、大小和访问权限。vDSO首地址为第二个映射区域的首地址。
/// 
/// 在调用该库的其余API前，需先调用此函数。
pub fn () -> Vec<(*mut u8, usize, MappingFlags)>
```
函数功能：
1. 调用`load_so`

   1. 分配空间并确定加载的初始地址

   2. 加载vvar部分（在对应地址调用`VvarData::default()`），对应一个内存区域

   3. 加载vdso部分

      1. 解析so文件中的段，按段拷贝到对应位置，每段对应一个内存区域

      2. 解析so文件中需要重定位的位置并重定位

   4. 返回内存区域数组

2. 调用`init_vdso_vtable`

   1. 根据so文件的加载地址和函数在so文件内的偏移量，计算每个函数的地址并填充到`VDSO_VTABLE`中。

      1. 注：`VDSO_VTABLE`位于编译出的api库中，编译后会进入主编译单元的数据段。不属于vDSO的共享数据或私有数据。

3. 返回`load_so`返回的vdso内存区域数组。

#### MemIf

```plain
/// 在内核初始化时加载vDSO使用的接口。
/// 
/// 实现了这些接口后，可以调用`loader::load_so`或`api::load_and_init`
#[def_interface]
pub trait MemIf {
    /// 分配用于vDSO和vVAR的空间，返回指向首地址的指针。
    /// 
    /// 保证size为build_vdso传入的config.page_size的整数倍；
    /// 要求返回的地址也为config.page_size的整数倍。
    ///
    /// 若需要实现vDSO和vVAR在多地址空间的共享，则需要在分配时使这块空间可被共享。
    fn alloc(size: usize) -> *mut u8;

    /// 从`alloc`返回的空间中，设置其中一块的访问权限。
    /// 
    /// 保证addr对齐到build_vdso传入的config.page_size；len为config.page_size的整数倍。
    /// 如果从so文件中解析出的段基址不对齐，则panic；段长度不为config.page_size的整数倍则向上取整。
    ///
    /// `flags`可能包含：READ、WRITE、EXECUTE、USER。
    fn protect(addr: *mut u8, len: usize, flags: MappingFlags);
}
```
### 用户态映射与初始化

首先，需要在内核调用`map_so`将vDSO映射到用户态。之后，通过辅助向量等方式将vDSO基址提供给用户。最后，由用户调用`init_vdso_vtable`初始化vDSO。之后就可在用户态使用vDSO。

（`init_vdso_vtable`的功能见上文）

#### map_so

```plain
/// 将已加载的vdso映射到另一个地址空间。
/// 
/// 该函数的返回值为vDSO和vVAR的映射区域的信息，元组的四项依次为用户虚拟地址、内核虚拟地址、大小和访问权限。vDSO首地址为第二个映射区域的首地址。
/// 
/// 需在内核调用此函数映射到用户空间，再在用户空间中调用`init_vdso_vtable`。
pub fn map_so(vspace: usize) -> Vec<(*mut u8, *mut u8, usize, MappingFlags)>
```
函数功能：
1. 在用户空间分配一块区域（不会同时分配物理页），获得用户空间加载首地址

2. 获取存储在内核的内核空间加载首地址

3. 映射vvar部分：直接将vvar所在的物理页映射到用户空间对应地址

4. 映射vdso部分：

   1. 从so文件解析每个段

      1. 如果为代码段（设置了可执行标记），则直接将其加载到内核的物理页（注意：和so文件本身存储的内存位置不同）映射到用户空间对应地址

      2. 如果为数据段（未设置可执行标记），则在内核分配新的物理页，将so文件中的内容拷贝过去，重定位，并将该物理页映射到用户空间对应地址

#### UserMemIf

由`map_so`函数调用，请求操作系统相关功能的接口。

除此之外，`map_so`函数还会调用`MemIf::alloc`。

```plain
/// 将已加载的vDSO映射到其它地址空间使用的接口。
/// 
/// 实现了这些接口后，可以调用`loader::map_so`
#[def_interface]
pub trait UserMemIf {
    /// 在地址空间中分配用于vDSO和vVAR的虚存区域（不需同时分配物理页面），返回指向首地址的指针。
    /// 
    /// 保证size为build_vdso传入的config.page_size的整数倍。
    /// 要求返回的地址也为config.page_size的整数倍。
    fn ualloc(vspace: usize, size: usize) -> *mut u8;

    /// 从`alloc`返回的虚存区域中，映射其中一块到某个内核虚拟地址所指示的物理页面并设置权限。
    /// 
    /// 被映射的物理页面可能和其它地址空间共享，也可能由这个地址空间独占。
    /// 
    /// 保证uaddr、kaddr对齐到build_vdso传入的config.page_size；len为config.page_size的整数倍。
    ///
    /// `flags`可能包含：READ、WRITE、EXECUTE、USER。
    fn map(vspace: usize, uaddr: *mut u8, kaddr: *mut u8, len: usize, flags: MappingFlags);
}
```
## Alien移植时的问题

### 物理页保存问题

Alien沿用了rcore的设计，使用FrameTracker持有物理页，并实现drop trait，从而实现自动释放。因此，分配页的函数会返回一个FrameTracker对象，而不仅仅是一个地址。

MemIf中的alloc接口实现中，通过alloc_frame_trackers分配连续物理页帧，但是只返回物理地址，FrameTracker如果不保存会自动drop，这显然是不好的。

但是，只有到了protect/map才能将FrameTracker对象保存到VmSpace对象中，因此中间需要暂存

### 区分两种页分配

alloc会被调用多次，分为2种情况：

1. 分配所有进程共享的vvardata以及.text，.rodata等只读段

2. 分配每个进程独占的.bss，.data等读写段

这两种页都需要暂存，分别在protect/map中取出
